# پدل کلاب — MVP مدیریت مچ‌میکینگ پدل

وب‌اپ فارسی و RTL برای مدیریت بازیکنان، مسابقات هشت‌نفره روی دو زمین، ثبت امتیاز سه ست، رتبه‌بندی مسابقه و لیدربرد عمومی. تمام داده‌های محصول از Supabase خوانده می‌شوند؛ داده نمایشی یا حساب مدیر پیش‌فرض وجود ندارد.

## اجرای پروژه

پیش‌نیاز: Node.js نسخه 20.9 یا بالاتر (پیشنهاد: Node 24 LTS)، npm و یک پروژه Supabase.

```bash
cd padel-club
npm ci
cp .env.example .env.local
```

متغیرهای محیطی را تنظیم و SQL بخش بعد را اجرا کنید، سپس:

```bash
npm run dev
```

آدرس برنامه: http://localhost:3000

نسخه production:

```bash
npm run build
npm start
```

بدون env، مسیرهای وابسته به دیتابیس صفحه راه‌اندازی را نمایش می‌دهند. پس از تغییر env، سرور توسعه را دوباره اجرا کنید؛ برای production دوباره build بگیرید. فونت Vazirmatn داخل بسته پروژه میزبانی می‌شود و به Google Fonts وابسته نیست.

## متغیرهای محیطی

```dotenv
NEXT_PUBLIC_SUPABASE_URL=https://YOUR_PROJECT.supabase.co
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
```

این دو مقدار را از تنظیمات پروژه Supabase، بخش API / API Keys بردارید. برای پروژه‌های قدیمی می‌توان کلید عمومی `anon` را در همان متغیر دوم قرار داد. کلید `service_role` یا secret key را در هیچ متغیر `NEXT_PUBLIC_` نگذارید؛ برنامه به آنها نیاز ندارد. `.env.local` در Git ثبت نمی‌شود.

## SQL موردنیاز Supabase

فایل کامل، تراکنشی و مرجع دیتابیس:

**[supabase/migrations/001_initial.sql](supabase/migrations/001_initial.sql)**

در یک پروژه خالی Supabase، تمام محتوای این فایل را در **SQL Editor → New query** اجرا کنید. اسکریپت فقط یک بار اجرا می‌شود؛ برای تغییرات بعدی migration تازه بسازید. این فایل شامل تمام جدول‌ها، کلیدهای خارجی، ایندکس‌ها، RLS، مجوزها، توابع و viewهای عمومی است. برای جدول‌های ساخته‌شده از قبل اجرا نشود.

توابع اصلی:

| تابع | کاربرد |
| --- | --- |
| `is_admin()` | تشخیص ادمین براساس کاربر احراز هویت‌شده |
| `create_tournament(title, date, player_ids)` | تخصیص تصادفی اسلات و ساخت ۷ دور، ۱۴ بازی، ۴۲ ست و ۸ نتیجه اولیه |
| `start_tournament(tournament_id)` | تغییر وضعیت آماده به فعال |
| `save_match_scores(match_id, version, sets)` | ثبت/اصلاح اتمیک سه جایگاه ست و بازسازی رتبه‌بندی |
| `recalculate_tournament_standings(tournament_id)` | محاسبه مجدد آمار از داده خام؛ فقط مسابقات نهایی‌نشده |
| `finish_tournament(tournament_id)` | بررسی تکمیل تمام بازی‌ها، بازسازی نهایی و قفل مسابقه |

نام پارامترهای RPC در کد SQL با `p_` شروع می‌شود. مثال بازسازی دستی، فقط از یک session احراز هویت‌شده ادمین:

```sql
select public.recalculate_tournament_standings('TOURNAMENT_UUID'::uuid);
```

فراخوانی توابع وابسته به `auth.uid()` در SQL Editor معمولی، بدون session کاربر، عمداً `ADMIN_REQUIRED` برمی‌گرداند. عملیات عادی را از داخل اپ انجام دهید؛ ساخت ادمین استثناست و با دسترسی مالک دیتابیس انجام می‌شود.

## نحوه ساخت Admin

1. در **Supabase → Authentication → Users → Add user → Create new user** یک حساب با ایمیل و رمز قوی بسازید و ایمیل را تأیید کنید (Auto Confirm).
2. در SQL Editor، ایمیل همان حساب را در دستور زیر جایگزین کنید:

```sql
insert into public.admins (user_id)
select id
from auth.users
where lower(email) = lower('admin@example.com')
on conflict (user_id) do nothing;

-- بررسی اینکه حساب به فهرست ادمین‌ها اضافه شده است:
select u.email, a.created_at
from public.admins a
join auth.users u on u.id = a.user_id;
```

3. به `/login` بروید و با همان ایمیل و رمز وارد شوید.
4. ثبت‌نام عمومی را در تنظیمات Auth غیرفعال کنید؛ فرم ثبت‌نام عمومی در برنامه وجود ندارد. داشتن حساب Auth به‌تنهایی دسترسی مدیریتی نمی‌دهد.
5. Site URL را برای توسعه `http://localhost:3000` و برای انتشار دامنه واقعی برنامه قرار دهید. ورود فعلی با ایمیل/رمز است و callback جداگانه نمی‌خواهد.

حذف دسترسی ادمین (از SQL Editor):

```sql
delete from public.admins
where user_id = (select id from auth.users where lower(email) = lower('admin@example.com'));
```

مدیریت ادمین‌ها از UI یا metadata قابل انجام نیست. رمز عبور را در فایل SQL یا سورس نگذارید.

## مسیر استفاده

1. در `/players` حداقل هشت بازیکن ثبت کنید. شماره موبایل اختیاری و غیرمنحصربه‌فرد است.
2. در `/tournaments/new` عنوان، تاریخ و دقیقاً هشت بازیکن متفاوت را انتخاب کنید.
3. برنامه بازی‌ها به‌صورت تراکنشی ساخته می‌شود. اسلات‌ها در بخش بازشدنی صفحه مسابقه قابل مشاهده‌اند.
4. «شروع مسابقه» را بزنید؛ امتیازهای هر زمین را ثبت کنید. ثبت بخشی از ست‌ها هم ممکن است.
5. بعد از ثبت هر سه ست، بازی کامل و تیم برنده مشخص می‌شود. جدول با هر ذخیره به‌روز می‌شود.
6. پس از تکمیل ۱۴ بازی، «پایان مچ‌میکینگ» را تأیید کنید. نتایج قفل و در صفحه عمومی و لیدربرد منتشر می‌شوند.

## تصمیم‌های امتیازدهی

- هر سه ست همیشه اجرا می‌شوند؛ بردن دو ست اول، ست سوم را حذف نمی‌کند.
- هر ست دو امتیاز صحیح متفاوت بین ۰ و ۹۹ دارد، یا هر دو امتیاز آن خالی‌اند. صفر با خالی متفاوت است. اعداد فارسی و عربی نرمال می‌شوند.
- محدودیت ست استاندارد تنیس مثل ۶–۴ یا ۷–۵ اعمال نشده؛ فرمت باشگاهی قابل استفاده است. امتیاز مساوی پذیرفته نمی‌شود.
- هر دو بازیکن، امتیاز تیم خود را دریافت می‌کنند. تفاضل برابر امتیاز کسب‌شده منهای امتیاز دریافت‌شده است.
- ست کامل در بازی ناتمام وارد جدول می‌شود؛ برد/باخت بازی فقط وقتی هر سه ست ثبت شده باشد محاسبه می‌شود.
- رتبه: امتیاز بیشتر، سپس برد ست بیشتر، سپس تفاضل بهتر. در تساوی کامل، ترتیب اسلات تصادفی اولیه A–H تعیین‌کننده است. رتبه‌ها ۱ تا ۸ و یکتا هستند.
- اصلاح یا پاک‌کردن ست پیش از نهایی‌سازی مجاز است؛ آمار از ابتدا محاسبه می‌شود و امتیاز تکراری جمع نمی‌شود.
- لیدربرد فقط مسابقات پایان‌یافته را جمع می‌کند: تاج بیشتر، میانگین رتبه کمتر، سپس درصد برد بیشتر. در تساوی کامل شناسه بازیکن ترتیب ثابت می‌دهد.
- درصد برد = برد بازی / مجموع بازی‌های کامل × ۱۰۰. میانگین امتیاز پروفایل، میانگین امتیاز مسابقات پایان‌یافته است.
- نشان‌ها از مسابقات پایان‌یافته محاسبه می‌شوند. «روی فرم» یعنی حداقل پنج برد پی‌درپی در **آخرین** بازی‌ها. ترتیب بازی‌ها تاریخ مسابقه، زمان ایجاد، شماره دور و زمین است؛ تاریخ ثبت/ویرایش امتیاز ترتیب را تغییر نمی‌دهد. «امتیاززن» به همه بازیکنان با بیشترین تفاضل یک مسابقه تعلق می‌گیرد.
- تاریخ ورودی HTML میلادی است؛ نمایش تاریخ فارسی/جلالی و منطقه زمانی تهران است.

## معماری و ساختار

- Next.js 16.3.5 با App Router، React، TypeScript strict، Tailwind CSS 4، کامپوننت‌های قابل ویرایش بر پایه الگوی shadcn/ui و Radix، Lucide، Sonner و Zod.
- Server Components برای خواندن داده؛ Client Components برای فرم، فیلتر و ثبت امتیاز؛ Server Actions برای تغییر داده.
- Supabase SSR با cookies، بررسی claims و عضویت ادمین در خواندن‌ها و عملیات مدیریتی. Proxy برای تمدید session.
- PostgreSQL مرجع محاسبات است؛ منطق فرانت‌اند نمی‌تواند مجوزها یا نتایج را دور بزند.

```text
src/
  app/
    (admin)/                 # محافظت‌شده، شامل داشبورد
      players/[id]/
      tournaments/new/
      tournaments/[id]/
    (public)/
      leaderboard/
      tournaments/[id]/results/
    login/  setup/
    actions.ts               # mutationها و اعتبارسنجی
  components/
    ui/                      # Button / Input / Dialog
    forms.tsx
    tournament-board.tsx     # MatchCard / ScoreInput / RoundNavigator
    shared.tsx               # Avatar / Standings / Podium / Badges / Stats
    shell.tsx                # sidebar و ناوبری موبایل
  lib/
    supabase/                # کلاینت SSR و نوع‌های دیتابیس
    tournament/
      generateMatches.ts     # برنامه ثابت قابل توسعه
      badges.ts
    auth.ts  data.ts  validation.ts
  proxy.ts
supabase/migrations/001_initial.sql
tests/                       # فقط داده آزمون؛ وارد محصول نمی‌شوند
```

| مسیر | دسترسی |
| --- | --- |
| `/`, `/players`, `/players/[id]` | ادمین |
| `/tournaments`, `/tournaments/new`, `/tournaments/[id]` | ادمین |
| `/tournaments/[id]/results` | عمومی؛ فقط مسابقه تکمیل‌شده |
| `/leaderboard` | عمومی |
| `/login`, `/setup` | عمومی |

### یکپارچگی و حریم خصوصی

- تمام جدول‌های پایه RLS دارند. نوشتن مستقیم برنامه بازی‌ها و نتایج حتی برای نقش authenticated مجاز نیست؛ فقط RPC ادمین.
- RPCهای حساس `security definer` با `search_path` خالی، نام جدول‌های صریح و بررسی `is_admin()` هستند.
- viewهای عمومی عمداً با دسترسی مالک اجرا می‌شوند اما فقط ستون‌های مشخص، نام بازیکن و آمار مسابقات تکمیل‌شده را برمی‌گردانند. شماره موبایل در آنها نیست.
- ثبت نتیجه و پایان مسابقه یک قفل مشترک روی تورنمنت دارند. `version` بازی از بازنویسی نتیجه جدید با فرم قدیمی جلوگیری می‌کند.
- حذف بازیکنی که سابقه مسابقه دارد با کلید خارجی مسدود است؛ بازیکن بدون سابقه با تأیید قابل حذف است.
- نتایج پایان‌یافته از داخل اپ قابل بازگشایی نیستند.

## تست و اعتبارسنجی

```bash
npm run typecheck
npm run lint
npm test
npm run build
```

تست دیتابیس فایل migration واقعی را روی PostgreSQL داخل PGlite اجرا می‌کند؛ فقط جدول کوچک `auth.users` و `auth.uid()` محیط Supabase برای آزمون فراهم می‌شوند. موارد تحت پوشش: برنامه دقیق، هفت هم‌تیمی متفاوت، ساخت اتمیک، ست ناقص، اصلاح و پاک‌کردن نتیجه، کنترل version، ورودی نامعتبر، ترتیب رتبه، جمع امتیازها، پایان زودهنگام، قفل نهایی، RLS ادمین/کاربر عادی/ناشناس، محرمانگی شماره و نشان‌ها.

تست مرورگر مستقل از Supabase زنده:

```bash
npx playwright install chromium
npm run test:e2e
```

این تست‌ها روی build نسخه production اجرا می‌شوند. این تست‌ها صفحه راه‌اندازی، ورود، محافظت مسیرها، پنل، فرم امتیاز، دیالوگ بازیکن و انتخاب هشت نفر را در دسکتاپ و موبایل کنترل می‌کنند. داده و سرویس احراز هویت در تست مرورگر، fixture مستقل داخل `tests/browser/backend.mjs` است و هرگز وارد محصول نمی‌شود؛ صحت محاسبات و مجوزها جداگانه با SQL واقعی آزمایش می‌شود. اگر Chrome نصب است، می‌توانید به‌جای نصب مرورگر از `PLAYWRIGHT_CHANNEL=chrome npm run test:e2e` استفاده کنید. برای پذیرش نهایی روی پروژه واقعی، با یک حساب ادمین چرخه «ثبت ۸ بازیکن → ساخت → شروع → ثبت ۱۴ نتیجه → پایان → مشاهده نتایج عمومی» را اجرا کنید. تست PostgreSQL محلی جای آزمایش ارتباط شبکه و تنظیمات پروژه Supabase واقعی را نمی‌گیرد.

برای سازگاری با محیط اجرای محدود، دستورهای dev و build از Webpack استفاده می‌کنند.

## حدود MVP

فرمت فعلاً دقیقاً ۸ نفر، ۲ زمین و ۷ دور است. تغییر فرمت نیاز به migration و تغییر generator دارد؛ تست، تطابق برنامه TypeScript و SQL را کنترل می‌کند. جدول زنده پس از ذخیره و با دکمه تازه‌سازی به‌روز می‌شود؛ push هم‌زمان با Supabase Realtime در این نسخه اضافه نشده است. برای ویرایش نتایج تکمیل‌شده یا فرمت‌های دیگر، جریان محصول جداگانه لازم است.

منابع پیاده‌سازی: [Next.js Proxy](https://nextjs.org/docs/app/getting-started/proxy)، [Supabase SSR](https://supabase.com/docs/guides/auth/server-side/creating-a-client).
