# مچ شو / MatchSho — پلتفرم فارسی رزرو و هم‌بازی

[راهنمای Docker، Supabase سلف‌هاست و انتقال دامنه](docs/SELF-HOSTING.md): نصب روی سرور `85.198.55.121`، دامنهٔ `match-sho.com`، انتقال کاربران/فایل‌ها، مایگریشن امن، HTTPS و بکاپ. نقطهٔ شروع: `bash deploy/setup.sh match-sho.com api.match-sho.com YOUR_REAL_EMAIL`؛ دیتابیس فعلی را قبل از مطالعهٔ مسیر انتقال دست‌کاری نکنید.

[اصلاح رابط رزرو و هویت مچ شو](docs/MATCHSHO-UI-REFINEMENTS.md): منوی مستقل بررسی واریزها در `/admin/payments`، ناوبری ثابت موبایل و قدم‌های تطبیقی رزرو.

[رزرو مرحله‌ای، تنظیمات روش‌های پرداخت و کارت‌به‌کارت](docs/CARD-TRANSFER-AND-BOOKING-WIZARD.md): شماره کارت و نام مقصد در `/admin/settings` تنظیم می‌شود؛ رسیدهای خصوصی با تأیید/ردِ دلیل‌دار مدیر بررسی می‌شوند. قواعد اکشن اصلی/ثانویه در `DESIGN.md` الزامی‌اند.

راهنمای جدید [صف اقدام مدیر، پیشنهاد سانس جایگزین، ورود پیامکی و Firebase](docs/BOOKING-OPERATIONS-NOTIFICATIONS.md) شامل متغیرهای محیطی و مراحل فعال‌سازی است. ارسال بیرونی پیامک و پوش تا تنظیم حساب‌های سرویس فعال نمی‌شود.

رزرو خصوصی جدید با پرداخت اولیه و سپس تأیید نهایی ظرفیت انجام می‌شود. ورود، عضویت و تکمیل نام و سطح بازی داخل صفحهٔ رزرو است؛ سانس و تجهیزات انتخابی در مسیر احراز هویت حفظ می‌شوند. قرارداد سفارش‌های قبلی و بازی‌های باز تغییر نکرده است.

توسعه افزایشی MVP موجود با Next.js App Router، React، TypeScript، Supabase PostgreSQL/Auth/Storage، Tailwind و Radix. صفحه عمومی، رزرو خصوصی، بازی چهار نفره، امریکانو، حساب کاربری، مدیریت عملیات و اتصال server-side زرین‌پال اضافه شده‌اند. داده‌های تاریخی و موتور رتبه‌بندی قبلی حفظ می‌شوند. داده نمایشی و تأیید ساختگی وارد محصول نمی‌شود.

## اجرای پروژه

Node.js حداقل 20.9 و npm لازم است:

```bash
cd padel-club
npm ci
cp .env.example .env.local
npm run dev
```

پس از تنظیم env و اعمال migration روی محیط مناسب، آدرس توسعه [localhost:3000](http://localhost:3000) است.

```bash
npm run build
npm start
```

بدون Supabase، صفحات عمومی وضعیت راه‌اندازی/نبود اطلاعات واقعی نشان می‌دهند. فونت فارسی محلی است. پس از تغییر env سرور را restart و نسخه production را rebuild کنید.

## متغیرهای محیطی

| متغیر                                | کاربرد                                                          |
| ------------------------------------ | --------------------------------------------------------------- |
| NEXT_PUBLIC_SUPABASE_URL             | آدرس پروژه Supabase موجود                                       |
| NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY | کلید عمومی publishable یا anon                                  |
| NEXT_PUBLIC_SITE_URL                 | دامنه قطعی HTTPS؛ توسعه http://localhost:3000                   |
| SUPABASE_SECRET_KEY                  | فقط سرور؛ secret key یا service_role پروژه برای verify و worker |
| ZARINPAL_MERCHANT_ID                 | UUID پذیرنده زرین‌پال؛ فعلاً خالی                               |
| ZARINPAL_SANDBOX                     | true فقط آزمایشی؛ production برابر false                        |
| CRON_SECRET                          | secret قوی scheduler برای /api/jobs                             |
| BOOKING_PROVIDERS_JSON               | اتصال middleware مجاز باشگاه؛ پیش‌فرض {}                        |

فقط سه متغیر اول عمومی‌اند. هرگز secret/service_role یا token باشگاه را در NEXT_PUBLIC_ یا Git نگذارید. بدون تنظیمات درگاه پرداخت غیرفعال است؛ ورود، پروفایل و درخواست دستی مستقل قابل بررسی‌اند.

3. `20260923221728_delete_tournament.sql` — حذف تورنمنت.
4. `20261022111028_platform_expansion.sql` — شهر، باشگاه، سانس، تجهیزات، پروفایل، رزرو، پرداخت و RLS.

در دیتابیس **آزمایشی خالی** تمام فایل‌ها به ترتیب اجرا می‌شوند:

```bash
supabase start
supabase migration up
```

روی پروژه موجود **SQL قدیمی را دوباره اجرا نکنید و reset نزنید**. migrationهای توسعه و فعال‌سازی cron با تأیید کاربر روی production اعمال شده‌اند؛ نام فایل‌ها با تاریخچه واقعی هم‌تراز است. پیش از تغییر بعدی پشتیبان بگیرید. تغییر schema بعدی با `supabase migration new descriptive_name` ساخته شود؛ فایل اجراشده را تغییر ندهید. [گزارش انتشار](docs/DEPLOYMENT-20261022.md) وضعیت جدید را ثبت می‌کند.

## نحوه ساخت Admin

در Supabase → Authentication → Users حسابی با ایمیل واقعی و رمز قوی بسازید یا ثبت‌نام کاربر را تأیید کنید. سپس با SQL Editor مالک دیتابیس:

```sql
insert into public.admins(user_id)
select id from auth.users
where lower(email)=lower('admin@example.com')
on conflict(user_id) do nothing;

select u.email, a.created_at
from public.admins a join auth.users u on u.id=a.user_id;
```

با همان ایمیل در `/login` وارد شوید؛ مقصد ادمین `/admin` و کاربر عادی `/account` است. داشتن Auth یا user_metadata مجوز مدیریت نیست. حذف دسترسی:

```sql
delete from public.admins
where user_id=(select id from auth.users where lower(email)=lower('admin@example.com'));
```

ثبت‌نام عمومی، SMTP، تأیید ایمیل، Site URL و callbackها را طبق راهنمای عملیات تنظیم کنید. حساب پیش‌فرض وجود ندارد. اتصال بازیکن تاریخی به حساب جدید فقط پس از احراز هویت و انتخاب صریح مدیر انجام می‌شود.

## قواعد مالی و امتیازدهی

- همه مبالغ integer ریال؛ نمایش تومان. همه ورودی‌ها و نمایش‌های تاریخ شمسی‌اند و ساعت‌ها به‌صورت ۲۴ ساعته در منطقه `Asia/Tehran` نمایش و تفسیر می‌شوند.
- رزرو دستی تا مرجع واقعی و مهلت نگه‌داشت باشگاه پرداخت ندارد. مهلت حداکثر یک ساعت و محدود به hold/شروع/cutoff است.
- در بازی باز، زمین و تجهیزات مشترک چهار قسمت، تجهیزات شخصی و کارمزد مستقل‌اند. باقیمانده integer به یک سهم اضافه و مجموع دقیقاً برابر قیمت مرجع می‌شود.
- جایگاه تازه حداکثر ۱۰ دقیقه و محدود به hold است. چهار پرداخت باید تا چهار ساعت قبل شروع کامل شوند؛ وگرنه لغو و درخواست استرداد کامل ثبت می‌شود.
- تأیید دستی فقط پس از پرداخت‌های معتبر و hold معتبر؛ خودکار فقط پس از مرجع authoritative باشگاه. callback یا timeout موفقیت محسوب نمی‌شود.
- verify با مبلغ دیتابیس و مرجع یکتا؛ پرداخت دیرهنگام، جایگاه آزادشده را اشغال نمی‌کند و وارد پیگیری استرداد می‌شود.
- امریکانو همان هشت نفر، دو زمین، هفت دور، ۱۴ بازی و سه راند هر بازی است. برد دو راند، برد بازی است. رتبه: برد بازی، برد راند، تفاضل راند و اسلات اولیه. leaderboard فقط تورنمنت پایان‌یافته را جمع می‌کند.
- نتیجه دوستانه ریتینگ را تغییر نمی‌دهد. تغییر رقابتی نیازمند چهار شرکت‌کننده معتبر، تأیید هر دو تیم، سطح تأییدشده و تصمیم قابل audit مدیر است. ریتینگ با قبل/بعد ذخیره و بردهای تاریخی بازنویسی نمی‌شوند.
- تورنمنت عمومی ثبت‌نام، ظرفیت و رتبه/امتیاز نهایی پایه دارد؛ bracket پیشرفته اضافه نشده است.

## تست

```bash
npm run lint
npm run typecheck
npm test
npm run build
npx playwright install chromium
npm run test:e2e
```

با Chrome نصب‌شده: `PLAYWRIGHT_CHANNEL=chrome npm run test:e2e`.

تست SQL تمام migrationهای واقعی را روی PostgreSQL داخل PGlite اجرا می‌کند: حفظ تاریخچه، RLS، قیمت/موجودی، ظرفیت، مهلت، verify تکراری، استرداد و رویداد. تست مرورگر روی build production دسکتاپ/موبایل با `tests/browser/postgres-backend.mjs` است؛ Auth مرزی آزمون، اما داده و عملیات SQL/RLS واقعی‌اند. fixture هرگز وارد محصول نمی‌شود.

PGlite جای Supabase staging، Storage، SMTP، شبکه پرداخت و race چند اتصال را نمی‌گیرد. اطلاعات پذیرنده و API باشگاه بعداً تنظیم می‌شوند؛ پرداخت/رزرو خارجی واقعی هنوز آزمون پذیرش نشده‌اند.

## انتشار و حدود عملیاتی

[ممیزی و معماری](docs/EXPANSION.md) و [بکاپ، migration، زرین‌پال، cron، API و rollback](docs/OPERATIONS.md) بخشی از تحویل‌اند. scheduler باید عملاً فعال و بررسی شود. استرداد بانکی فعلاً پس از واریز واقعی توسط مدیر ثبت می‌شود؛ اعلان‌ها داخل حساب‌اند و ارسال ایمیل/SMS اضافه نشده است.

صفحات عمومی HTML قابل خزیدن، metadata/canonical، JSON-LD واقعی، sitemap و robots دارند. حساب/پرداخت/مدیریت و بازی‌های کوتاه‌عمر noindex هستند. فونت محلی، SVG سبک، تصاویر بهینه و reduced-motion استفاده شده‌اند. اهداف LCP≤2.5s، INP≤200ms و CLS≤0.1 باید در production با داده واقعی اندازه‌گیری شوند.

منابع: [Supabase SSR](https://supabase.com/docs/guides/auth/server-side/creating-a-client)، [RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)، [زرین‌پال](https://www.zarinpal.com/docs/paymentGateway/connectToGateway).

## همگام‌سازی تقویم باشگاه‌ها

پنل `/admin/integrations` سه منبع واقعی گیلان پدل، سرزمین صبا و تنیس رسپینا را مدیریت می‌کند. رسپینا از فهرست عمومی زمین‌ها و تقویم ساعتی `respina.gildev.ir` خوانده می‌شود؛ این اتصال در سایت رسپینا رزرو ایجاد نمی‌کند. فاصله پیش‌فرض ۶۰ دقیقه، قابل تنظیم از ۱۵ تا ۱۴۴۰ دقیقه، و افق تقویم ۱ تا ۱۴ روز است. ابتدا باشگاه مقصد را ذخیره و زمین‌های آن را به زمین‌های کشف‌شده منبع وصل کنید. بدون نگاشت، فقط اتصال و فهرست زمین‌ها بررسی می‌شود و وضعیت «نیازمند انتساب» نمایش داده می‌شود. زمین‌های A/B را با شماره واقعی باشگاه تطبیق دهید؛ نام مشابه به‌صورت حدسی نگاشت نمی‌شود.

دکمه «درخواست همگام‌سازی اکنون» اجرای بعدی را جلو می‌اندازد؛ زمان‌بند هر دقیقه اتصال‌های موعدرسیده را بررسی می‌کند. آخرین تلاش/موفقیت، نوبت بعدی، خطا، تعداد سانس‌ها و ۳۰ اجرای اخیر در پنل دیده می‌شوند. تغییر مقصد، قطع نگاشت یا غیرفعال‌سازی اتصال، سانس واردشده را از رزرو خارج می‌کند؛ رزرو قبلی و قیمت آن حفظ می‌شوند.

SQL کامل افزایشی در migrationهای `calendar_*.sql` قرار دارد؛ همه را به ترتیب زمانی اجرا کنید. پس از اجرای migrationها، Edge Function را منتشر کنید:

```bash
npx supabase functions deploy calendar-sync --project-ref YOUR_PROJECT_REF
```

سپس **یک‌بار** در SQL Editor مقصد واقعی function را تنظیم کنید:

```sql
select vault.create_secret(
  'https://YOUR_PROJECT_REF.supabase.co/functions/v1/calendar-sync',
  'calendar_worker_url'
);
-- در نصب‌های بعدی اگر این نام وجود دارد، به‌جای ایجاد مجدد از vault.update_secret استفاده کنید.
select private.dispatch_calendar_sync();
select jobname, schedule, active from cron.job where jobname = 'rallyyar-calendar-sync';
select source, status, last_attempt_at, last_success_at, next_sync_at, last_error
from public.calendar_connections;
```

migration افزونه pg_net را در Supabase فعال و توکن تصادفی خصوصی را داخل Vault می‌سازد. function قبل از هر کار آن را با RPC مخصوص `service_role` اعتبارسنجی می‌کند؛ `verify_jwt=false` در این function به معنی دسترسی عمومی به worker نیست. توکن را در README، کلاینت، لاگ یا env عمومی کپی نکنید. `SUPABASE_URL` و `SUPABASE_SERVICE_ROLE_KEY` داخل Edge Runtime به‌طور خودکار موجودند؛ **برای تقویم env جدیدی در Vercel لازم نیست**. cron این بخش مستقل از `/api/jobs` و worker پرداخت است؛ worker پرداخت همچنان تنظیمات و دسترسی جداگانه خود را لازم دارد.

آداپتورها فقط آدرس‌های ثابت رسمی را می‌خوانند: گیلان از صفحه و availability عمومی، صبا از گردش عمومی Bookly با جلسه ناشناس موقت. هیچ endpoint پرداخت، ثبت appointment، سبد خرید یا انتخاب سانس فراخوانی نمی‌شود. فعلاً ورود برای خواندن تقویم لازم نیست؛ در صورت تغییر دسترسی، وضعیت `login_required` ثبت می‌شود. رمز حساب شخصی ذخیره نمی‌شود. اجرای رزرو در سایت باشگاه نیازمند اتصال مجاز جداگانه و تأیید واقعی آن باشگاه است.

داده ناقص/تغییر ساختار منتشر نمی‌شود؛ داده‌ای که بیش از فاصله تنظیم‌شده + ۵ دقیقه قدیمی باشد یا اتصالش خطا داشته باشد، برای درخواست رزرو قابل استفاده نیست. سانس دستی با importer بازنویسی نمی‌شود و تعارض در گزارش ثبت می‌شود. قیمت‌ها از تومان منبع به ریال تبدیل می‌شوند؛ قیمت فعلی منبع تضمین قیمت یا hold نیست و تأیید مدیر قبل از پرداخت همچنان لازم است.

مستند زمان‌بندی: [Supabase Scheduled Functions](https://supabase.com/docs/guides/functions/schedule-functions).

## تخفیف، رزرو رایگان و معرفی باشگاه

رابط پنل در `/admin/operations` تب‌بندی شده است. رزرو را با نام، باشگاه، زمین یا شناسه پیدا کنید؛ دکمه «جزئیات و مدیریت» پرونده همان رزرو را باز می‌کند. تأیید باشگاه، بازیکنان، معافیت، پرداخت‌های مرتبط و لغو در همان پرونده‌اند. کدهای تخفیف، پرداخت و استرداد تب مستقل دارند. فهرست‌ها جست‌وجو، فیلتر وضعیت و صفحه‌بندی هشت‌تایی دارند. ساخت/ویرایش کاتالوگ و رویدادها و تنظیمات اتصال نیز در پنجره‌های مجزا انجام می‌شود.

در فرم رزرو، تب‌های «رزرو خصوصی زمین» و «بازی باز چهار نفره» توضیح، تقویم، فرم معرفی بازی، تجهیزات و خلاصه هزینه را متناسب با شیوه بازی نمایش می‌دهند. تغییر تب، سانس معتبر و تجهیزات را حفظ می‌کند؛ سانس ناسازگار با مهلت بازی باز پاک می‌شود و پذیرش شرایط باید برای حالت جدید انجام شود. کلیدهای چپ/راست، Home و End برای انتخاب تب پشتیبانی می‌شوند.

انتخاب تعداد تجهیزات در رزرو و پیوستن به بازی از استپر مشترک +/− استفاده می‌کند؛ سقف موجودی و مقدار صفر در رابط رعایت و دوباره روی سرور بررسی می‌شوند. لودینگ توپ، حساب بازیکن و پروفایل از قواعد [DESIGN.md](DESIGN.md) پیروی می‌کنند. این بازطراحی migration، env یا تغییر نقش کاربران لازم ندارد.

پس از نصب migration افزایشی `booking_benefits.sql`، بخش «کدهای تخفیف» در `/admin/operations` در دسترس است. کد انگلیسی، درصد یا مبلغ ثابت **به تومان**، سقف کل استفاده و انقضای شمسی با ساعت تهران را وارد کنید. هر حساب از هر کد یک بار استفاده می‌کند؛ کد را می‌توان غیرفعال کرد. بازیکن بعد از ثبت نگه‌داشت معتبر باشگاه، در `/account/bookings` کد را روی سهم خود اعمال می‌کند. هر سهم یک کد می‌پذیرد؛ استفاده در زمان اعمال مصرف می‌شود و با لغو یا انقضا برنمی‌گردد. محاسبه و کنترل ظرفیت در دیتابیس با قفل انجام می‌شود.

برای رزرو رایگان، ابتدا تأیید واقعی باشگاه و مهلت نگه‌داشت را ثبت کنید؛ سپس در «رزرو بدون پرداخت» سهم بازیکن را با دلیل معاف کنید. ادمین می‌تواند مانده پس از تخفیف را هم معاف کند. رزرو خصوصی با تسویه همان سهم، و بازی باز پس از تسویه چهار سهم و تأیید واقعی زمین قطعی می‌شود. مبلغ صفر به درگاه نمی‌رود و رسید بانکی ساختگی ایجاد نمی‌کند. اگر پرداختی در حال بررسی باشد، تغییر مبلغ تا تعیین تکلیف آن مسدود است. سابقه مبلغ اصلی، تخفیف و ادمین اقدام‌کننده در دیتابیس و گزارش حسابرسی حفظ می‌شود.

شمارش معکوس ثانیه‌ای از مهلت سرور استفاده می‌کند؛ اتمام شمارنده صفحه را تازه می‌کند و تصمیم نهایی اعتبار رزرو همچنان روی سرور است.

در `/admin/clubs` برای هر زمین ورزش (پدل، تنیس، تنیس ساحلی، اسکواش، بدمینتون یا سایر) انتخاب کنید؛ آیکون مناسب در صفحه باشگاه نمایش داده می‌شود. در همان پنل، عکس واقعی باشگاه، معرفی، آدرس و مختصات جغرافیایی را ثبت کنید. عکس در صفحه و پیش‌نمایش شبکه‌های اجتماعی و داده ساختاریافته SEO استفاده می‌شود؛ نقشه دقیق فقط با مختصات ثبت‌شده نمایش داده می‌شود. بدون مختصات، لینک جست‌وجوی آدرس ارائه می‌شود. این قابلیت‌ها env جدیدی لازم ندارند.
