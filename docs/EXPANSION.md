# توسعه پدل کلاب — ممیزی و طرح انتشار

## ممیزی، ۳۰ مهر ۱۴۰۵

نسخه فعلی Next.js 16 با App Router، React، TypeScript strict، Tailwind، Radix، Zod و Supabase SSR است. کد محلی به GitHub متصل و مبنای توسعه commit `44789f5` است. سه migration محلی با سه migration ثبت‌شده در Supabase از نظر نام و محتوا متناظرند؛ timestampهای اولیه متفاوت‌اند. migrationهای قدیمی دوباره روی محیط زنده اجرا نمی‌شوند.

پروژه موجود Supabase: `bcfbvxmwozmewshctzch`، PostgreSQL 17.6. بررسی read-only: ۲۰ بازیکن، ۲ تورنمنت، یک کاربر و یک ادمین. تمام جدول‌های فعلی RLS دارند. هیچ bucket، زیرساخت رزرو، درگاه، webhook یا job عملیاتی موجود نیست. داده و حساب تازه‌ای جایگزین این داده‌ها نمی‌شود.

رتبه‌بندی فعلی از migration شهریور به برد بازی، سپس برد راند و تفاضل راند تغییر کرده است؛ تاریخچه و این الگوریتم حفظ می‌شود. ستون‌های امتیاز عددی دیگر در دیتابیس زنده موجود نیستند. برنامه هشت‌نفره فعلی، هفت هم‌تیمی متفاوت به هر بازیکن می‌دهد و برای امریکانو قابل استفاده مجدد است.

اجزای قابل استفاده: احراز هویت cookie-based، بررسی ادمین دیتابیس، فرم‌ها، جدول‌ها، برنامه بازی‌ها، مدل نتایج و تست PostgreSQL. نیاز به توسعه: نقش کاربر عادی، پروفایل شخصی، مدیریت باشگاه و سانس، موتور رزرو و پرداخت، ایونت‌های قابل ثبت‌نام و صفحات عمومی SEO.

## تصمیم‌های سازگاری

- `/` صفحه عمومی و `/admin` داشبورد فعلی خواهد بود. `/players`، `/tournaments` و نتایج قبلی باقی می‌مانند. این جابه‌جایی تنها تغییر مسیر عمدی است.
- پروفایل Auth با شناسه کاربر مرتبط می‌شود. بازیکنان تاریخی به‌صورت خودکار با ایمیل یا موبایل ادغام نمی‌شوند؛ اتصال سابقه فقط با تأیید ادمین.
- مبالغ به ریال و به‌صورت integer ذخیره می‌شوند. نمایش تومان با تبدیل صریح است. همه زمان‌ها `timestamptz` و نمایش جلالی/تهران است.
- تمام رزروها به سانس معتبر متصل‌اند. قفل روی زمین، سانس و موجودی تجهیزات، و قیدهای یکتا از فروش هم‌زمان جلوگیری می‌کنند. درخواست دستی بدون تأیید باشگاه، رزرو قطعی نیست.
- پرداخت در سرور درخواست/verify می‌شود. callback یا پیام مرورگر به‌تنهایی اعتبار ندارد. نبود درگاه معتبر، پرداخت را متوقف می‌کند.
- اتصالات باشگاهی فقط از adapter مجاز و پیکربندی‌شده استفاده می‌کنند. آداپتر آزمون هرگز در محیط production انتخاب نمی‌شود.

## برنامه مهاجرت و بازیابی

تغییرات جدید افزایشی‌اند؛ هیچ migration قبلی و هیچ داده تاریخی حذف نمی‌شود. SQL جدید ابتدا روی PostgreSQL آزمون به‌همراه تمام migrationهای قبلی اجرا می‌شود. امنیت، رقابت برای ظرفیت، انقضای مهلت و idempotency بررسی می‌شوند.

قبل از اعمال زنده: پشتیبان schema و data با CLI رسمی و نگهداری امن خارج از Git، ثبت شمارش جدول‌های تاریخی، بررسی فضای دیتابیس و maintenance window. سپس تنها migrationهای جدید با تاریخچه ثبت‌شده اعمال و شمارش‌ها و مجوزها دوباره بررسی شوند. نسخه جدید اپ پس از موفقیت SQL منتشر می‌شود.

بازگشت کم‌خطر: بازگرداندن deployment قبلی؛ جدول‌های افزوده باقی بمانند و نوشتن جریان‌های جدید متوقف شود. حذف جدول یا restore بکاپ فقط با تأیید جداگانه و پس از بررسی پرداخت‌های واقعی. جزئیات در `OPERATIONS.md` تکمیل می‌شود.

اعمال migrationهای جدید روی production و انتشار نسخه جدید تا تکمیل بررسی و تأیید طرح پشتیبان متوقف است؛ توسعه محلی و تست‌ها ادامه دارند.
